| 项 | 值 |
|---|---|
| 状态 | **已接受** |
| 日期 | 2026-09 |
| 影响范围 | 阶段一 ~ 阶段三（全局） |
| 决策者 | 项目负责人 |
| 关联文档 | `AGENTS.md` §二 技术栈、§八 全局禁止事项 |

---

## 一、背景

阶段一需要选定 Agent 编排层。候选方案：

| 候选 | 版本（决策时） | 说明 |
|---|---|---|
| **LangGraph** | 1.2.11 | 图式编排，自带 `BaseCheckpointSaver` 抽象与 `PostgresSaver` 实现 |
| **pydantic-ai** | 2.45.0 | 自带图引擎 `pydantic-graph`，含 `deepseek` model profile，结构化输出（`output_type=`）体验优秀 |

`AGENTS.md` §二 技术栈表已声明「编排 = LangGraph，引入阶段 = 阶段一」。本 ADR 是对该声明的**正式复核**，不是事后补记。

---

## 二、决策

**采用 LangGraph 作为编排层。不引入 pydantic-ai。**

> **注**：本决策只针对 pydantic-**ai**（编排框架）。pydantic **v2** 与本次决策无关——它已是项目依赖（工具 Schema 自动生成的实现基础，见 `AGENTS.md` §五 原则 2），继续使用。

---

## 三、理由

### 3.1 决定性理由：短期记忆设计与 LangGraph 的 Checkpointer 强绑定

`AGENTS.stage2.md` 对短期记忆的定义存在**组件级依赖**，而非通用能力依赖：

| 出处 | 原文要求 |
|---|---|
| stage2 §4.1 | 「短期记忆：**PostgresSaver**，通过 `thread_id` 隔离。使用连接池，轮次上限默认 50 轮。**仅父图配置 Checkpointer，子图不单独配置**」 |
| stage2 验证 5 | 「Checkpointer 恢复：重启服务后，同一 `thread_id` 的会话能继续」 |
| stage2 §4.6 | 「Checkpointer 恢复的消息列表经转换后作为 `input` 数组传入」 |

`PostgresSaver` 是 LangGraph 独有组件。pydantic-ai 的等价机制是 `durable_exec`（DBOS / Temporal / Prefect），语义为**通用任务级工作流持久化**（崩溃后从哪个步骤续跑），**不提供**「按 `thread_id` 检索对话消息历史」这一能力。

**实测证据**：`pydantic_ai` 2.45.0 的模块树中不存在 `checkpoint` / `storage` / `message_history` 持久化模块，仅有：

```
pydantic_ai/durable_exec/
├── dbos/
├── prefect/
└── temporal/
```

采用 pydantic-ai 意味着 stage2 短期记忆设计全盘重写，其 13 条验证标准中至少 5 条失效。

### 3.2 自研消息转换层会被架空

`AGENTS.stage1.md` §4.4 要求**自行实现**「LangGraph ↔ Responses API」双向转换层，并明确要求「`web_search_call` | 保留，不过滤」。

该层是后续阶段的挂载点：

- 阶段二 §4.6：摘要压缩插在此层
- 阶段三 §4.8：`generation` 级 token / cost 插桩插在此层

pydantic-ai 有自成一体的 `ModelMessage` 体系与 provider 抽象，会接管该层。**结果是自研转换层被旁路，而阶段二、三的扩展点随之丢失。**

### 3.3 避免两套 LLM 抽象层

本项目为掌控 Responses API 的原始 item 结构（`function_call` / `function_call_output` / `reasoning` 保真），选择直连 `openai` SDK 而非 `langchain-openai`。若再引入 pydantic-ai，则同时存在：

1. `openai` SDK 原始响应
2. pydantic-ai 的 model 抽象层

阶段三的 Langfuse trace 与 token 计量需在两层分别插桩，且难以保证口径一致。

### 3.4 依赖成本

`pydantic-ai-slim==2.45.0` 解析出的直接依赖含：

```
opentelemetry-api==1.44.0
logfire-api==5.1.0
genai-prices==0.1.7
griffelib==2.3.0
pydantic-graph==2.45.0
```

对比：pydantic-ai 自带图引擎 `pydantic-graph`，与本项目采用的 LangGraph **功能重叠**。

---

## 四、代价（本决策承认的损失）

1. **结构化输出场景更啰嗦。** 阶段三的记忆抽取、CRAG 三分类、查询重写均为结构化输出场景。手搓 JSON 校验 + 重试逻辑，比 pydantic-ai 的 `output_type=SomeModel` 冗长，且容易漏掉边界（如模型返回非法 JSON 时的降级）。
2. **无法使用 pydantic-ai 的 model profile。** 例如其 `profiles/deepseek.py` 内置的模型特性声明。本项目的应对方式是自行维护 `DEEPSEEK_MODEL` 等配置。
3. **失去一个生态整合面。** pydantic-ai 与 Logfire 的原生集成（trace 可视）不可用；本项目改用 Langfuse（`AGENTS.md` §二 已声明）。

---

## 五、重新评估条件

满足以下**全部**条件时，重新开启本议题：

1. 阶段三出现 **≥ 3 处**结构化输出模块；
2. 手搓「JSON 解析 + 校验 + 重试」逻辑在 **≥ 2 个模块**中重复出现；
3. 该重复已被单元测试覆盖，且缺陷率表明手搓实现不可靠。

**若触发**，处置方式为：**在那些模块内局部引入 `pydantic-ai-slim` 仅做结构化输出，不改动编排层**。

> 若触发条件 1、2 但编排层也想换，则须新开 ADR-002 并先更新 `AGENTS.md` §二 技术栈表——依据 `AGENTS.md` §八：「在未更新 `AGENTS.md` 的情况下改变架构决策」为全局禁止事项。

## 六、决策依据数据

本 ADR 的结论基于以下实测（非推测）：

| 验证项 | 方法 | 结果 |
|---|---|---|
| pydantic-ai 是否支持 DeepSeek | 查看 `pydantic_ai/profiles/` | ✅ 有 `deepseek.py`，故「不支持 DeepSeek」**不构成**反对理由 |
| pydantic-ai 是否提供 Checkpointer | 检索模块树 | ❌ 无 `checkpoint`/`storage` 模块，仅 `durable_exec/{dbos,prefect,temporal}` |
| pydantic-ai 依赖体积 | `uv pip compile pydantic-ai-slim` | 引入 `opentelemetry-api`、`logfire-api`、`genai-prices`、`pydantic-graph` |
| 当前版本 | 包索引 | `pydantic-ai-slim==2.45.0` |
