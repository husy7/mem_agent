## ADR-001 编排层选型：LangGraph vs pydantic-ai

**完整决策文档见** [`docs/ADR-001-编排层选型.md`](./ADR-001-编排层选型.md)

| 候选 | 版本 | 结论 |
|---|---|---|
| LangGraph | 1.2.11 | ✅ **采用** |
| pydantic-ai | 2.45.0 | ❌ 不采用 |

**核心理由**（详细论证见 ADR）：

1. `pydantic-ai` 自带 `pydantic-graph`，与 LangGraph 功能重叠，引入等于维护两套图引擎
2. 无 `checkpoint` / `storage` 持久化能力（只有 `durable_exec/{dbos,prefect,temporal}`），
   而本项目阶段二要接 `PostgresSaver` + `PostgresStore`——这是硬需求
3. 它会引入自己的 LLM 抽象层，将**绕过**我们精心构建的 converter（为保 Responses API 的
   item 保真度），使阶段一的核心设计失效
4. 依赖成本：额外引入 `opentelemetry-api`、`logfire-api`、`genai-prices`

**pydantic v2 保持使用**——它已经是依赖，且负责工具 schema 生成，与编排层选型无关。

## EXP-01 pydantic-settings 嵌套配置为什么全部失效

### 现象

配置层改写完成后，**9 个测试同时失败**，其中 5 个 `test_invalid_config_fails_fast` 参数
全部报 `DID NOT RAISE`（非法配置没被拦截）。

### 原始症状

```
DEEPSEEK_MODEL 已在环境变量中设置，但 settings.llm.model 仍是 'deepseek-flash'（默认值）
SANDBOX_MAX_COMMANDS=42 被设置，但 settings.sandbox.max_commands 仍是 500
```

即：**环境变量完全没有被读取**，且不报任何错。

### 排查：5 种写法逐一实测

| # | 写法 | 结果 |
|---|---|---|
| 1 | 根上用 `Field(validation_alias="DEEPSEEK")` 指向嵌套 `BaseModel` | ❌ 完全不读环境变量 |
| 2 | 根上加 `env_nested_delimiter="__"`（配 `DEEPSEEK__MODEL`） | ❌ 无效 |
| 3 | 根上用 `Field(validation_alias="DEEPSEEK_")` | ❌ 无效 |
| 4 | **嵌套类继承 `BaseSettings` 并自带 `env_prefix`** | ✅ **成功** |
| 5 | 根上全部用扁平字段 | ✅ 成功（但组织性差） |
| 6 | 根上用 `env_prefix` | ✅ 成功（但只能有一个前缀） |

### 根因（两条）

**根因 1：嵌套的配置类必须继承 `BaseSettings`，不能继承 `BaseModel`。**

pydantic-settings 只对 `BaseSettings` 的子类执行「环境变量 → 字段」映射。
若嵌套类写成 `BaseModel`，它只做结构校验、完全不读环境变量——
**且不报错**，所以表现为「配置静默失效」。

**根因 2：`validation_alias` 的语义是「一个完整的环境变量名」，不是「前缀」。**

写 `Field(validation_alias="DEEPSEEK")` 意味着「去环境变量里找一个**名叫 `DEEPSEEK` 的变量**」，
而不是「找所有以 `DEEPSEEK` 开头的变量」。所以它永远匹配不到 `DEEPSEEK_API_KEY`。

### 采用方案

```python
class _GroupSettings(BaseSettings):        # ← 必须是 BaseSettings
    model_config = SettingsConfigDict(**COMMON)

class LLMSettings(_GroupSettings):
    model_config = SettingsConfigDict(**COMMON, env_prefix="DEEPSEEK_")   # ← 前缀在分组上
    model: str = "deepseek-flash"

class Settings(BaseSettings):
    llm: LLMSettings = Field(default_factory=LLMSettings)   # ← 根只负责组装，无 validation_alias
```

> 代码位置：`src/memagent/config.py`

## EXP-02 测试隔离怎么才能真的断开 `.env`

### 问题

单元测试要验证「字段默认值」，就必须在一个看不到 `.env` 的环境里构造 Settings。
但实测发现:**各分组继承了根的 `env_file` 配置**，所以它们自己也会读 `.env`。

实测证据（一次 `Settings()` 构造过程）：

```
.env 被打开 6 次（根 1 次 + 5 个分组各 1 次）
```

### 5 种隔离写法实测

| # | 写法 | 结果 | 原因 |
|---|---|---|---|
| 1 | `Settings(_env_file=None)` | ❌ 管不到分组 | 分组有自己的 `model_config['env_file']` |
| 2 | `LLMSettings(_env_file=None)` | ❌ **仍读 `.env`** | 同样被分组自己的配置覆盖 |
| 3 | `monkeypatch.setattr(config, "PROJECT_ROOT", 假路径)` | ❌ 无效 | `env_file` 在**类定义时**就求值成绝对路径了 |
| 4 | `monkeypatch.setenv("PYDANTIC_LLM_PREFIX", "")` | ❌ 无效 | 该机制不阻止分组读 `env_file` |
| 5 | **临时替换 `LLMSettings.model_config['env_file'] = None`** | ✅ **唯一有效** | 直接改 pydantic 实际读取的配置源 |

### 采用方案

```python
@contextmanager
def env_isolated(*groups: type[Any]) -> Iterator[None]:
    """临时让指定分组不读 .env，测「纯字段默认值」用。"""
    saved = []
    for group in groups:
        saved.append((group, dict(group.model_config)))
        patched = dict(group.model_config)
        patched["env_file"] = None
        group.model_config = patched
    try:
        yield
    finally:
        for group, original in saved:
            group.model_config = original     # ← 必须还原，否则污染后续所有测试
```

> 代码位置：`tests/unit/test_config.py` 的 `env_isolated()`

### 附带发现：Mock 默认值的陷阱（这个坑踩了三次）

**当 `.env` 里的值与字段默认值相同时，任何「隔离是否生效」的验证都是无效的。**

三次实例：

| # | 场景 | 现象 | 为什么无效 |
|---|---|---|---|
| 1 | 验证 `Settings(_env_file=None)` | 看起来"隔离成功" | 被检查的字段 `.env` 值恰好 == 默认值 |
| 2 | 验证 `env_isolated` | `SandboxSettings().max_commands` 前后都是 500 | `.env` 里 `SANDBOX_MAX_COMMANDS=500`，默认值也是 500 |
| 3 | 验证 `Settings(_env_file=None)` | `LLMSettings()` 的 `api_key` 看起来是 None | 当时 `.env` 里 key 恰好没设 |

**正确做法**：**用与默认值不同的判别值**验证。第二次验证时改写 `.env`
（`SANDBOX_MAX_COMMANDS=500 → 777`、`AGENT_MAX_STEPS=10 → 33`、`LOG_LEVEL=INFO → DEBUG`、
`WEB_SEARCH_MAX_RESULTS=5 → 19`），结果：

```
改写 .env 后（SAND=777, AGENT=33, LOG=DEBUG, WEB=19）
  不隔离:
    SandboxSettings().max_commands      = 777
    AgentSettings().max_steps           = 33
    LogSettings().level                 = 'DEBUG'
    WebSearchSettings().max_results     = 19
  隔离中（应全部回到字段默认值）:
    SandboxSettings().max_commands      = 500 (期望 500)
    AgentSettings().max_steps           = 10 (期望 10)
    LogSettings().level                 = 'INFO' (期望 INFO)
    WebSearchSettings().max_results     = 5 (期望 5)
```

这次才是真证据。该验证已固化为回归测试
`test_defaults_test_independent_of_env_file_content`。

### 另一个测试设计缺陷（由上一轮失败暴露）

`test_model_defaults_are_sane` 最初写成 `LLMSettings()`，
断言的是 `.env` 的值却拿字段默认值去比，表现为：

```
单独跑 → FAILED
全量跑 → PASSED    ← 因为全量时别的测试先清了环境变量
```

**「测试结果依赖执行集合」本身就是缺陷信号。**
一个测试的正确性不该取决于你跑了哪些别的测试。

## EXP-03 `validation_alias` vs `env_prefix` 谁赢

### 现象

`AgentSettings` 的 `tool_max_retries` 同时有 `env_prefix="AGENT_"`（继承自分组）
和 `validation_alias="TOOL_MAX_RETRIES"`。到底哪个环境变量生效？

### 实测输出

```
基线（都不设）:                  AgentSettings().tool_max_retries = 2
只设 TOOL_MAX_RETRIES=4        -> 4      ← 默认 2，说明 alias 生效
只设 AGENT_TOOL_MAX_RETRIES=5  -> 2      ← 仍是默认，说明 prefix 失效
```

### 结论

**`validation_alias` 覆盖 `env_prefix`。**

| 想设置 `tool_max_retries` | 是否生效 |
|---|---|
| `TOOL_MAX_RETRIES=2` | ✅ 生效 |
| `AGENT_TOOL_MAX_RETRIES=2` | ❌ **不生效**（静默失效） |

**本项目决定保留这个行为**：该字段描述的是「工具」的重试策略，脱开 agent 前缀更贴切。
但必须在 `.env` 与注释中明确标注，否则后来者一定会踩坑。

> 已固化为测试：`test_effective_env_var_names_are_documented`

## EXP-04 `.env` 与 OS 环境变量的优先级

### 实测

先设 `DEEPSEEK_MODEL=from-env`（OS 环境变量），同时 `.env` 里 `DEEPSEEK_MODEL=deepseek-flash`：

```
结果: model = 'from-env'      → OS 环境变量优先
```

### 结论与决策

| 来源 | 优先级 |
|---|---|
| OS 环境变量 | **更高** |
| `.env` 文件 | 较低 |

**本项目决策：只从 `.env` 读，不依赖 OS 环境变量。**

理由：避免「同一份 `.env` 在不同机器上（某台机器恰好 export 了同名变量）跑出不同结果」。
但这个优先级事实必须记录在案——因为它是 pydantic-settings 的既定行为，
我们**无法关闭**，只能约定不使用。

**对测试的影响**：本机 shell 若 export 过同名变量，会污染测试。
所以 `test_config.py` 有 `sanitize_env` autouse fixture，每个测试前后清理全部相关变量。

## EXP-05 python-dotenv 行内注释陷阱

### 现象

`.env` 中写了：

```dotenv
DEEPSEEK_API_KEY=            # 阶段二再定，先留空
```

读出来的值却是：

```
'# 阶段二再定，先留空'
```

### 结论

**python-dotenv 对「空值」的行内注释不生效，对「非空值」的才生效。**

| 写法 | 解析结果 |
|---|---|
| `KEY=abc  # 注释` | `'abc'`（注释被正确剥离） |
| `KEY=  # 注释` | `'# 注释'`（**注释变成了值**） |

### 采用方案

**注释一律单独占一行，不写在值后面。**

```dotenv
# 这一行是注释，单独占一行 —— 正确
DEEPSEEK_API_KEY=

DEEPSEEK_API_KEY=   # 这一行不是注释，它会让值变成 '# 这一行不是注释...' —— 错误
```

## EXP-06 pytest filterwarnings 的 module 参数不按预期工作

### 背景

原本在 `pyproject.toml` 里配置了：

```toml
filterwarnings = ["error::DeprecationWarning:memagent.*"]
```

意图：本项目代码产生的 `DeprecationWarning` 直接升级为错误，强制修复。

### 现象

**该配置从未生效过**——即使故意在本项目代码里触发 `DeprecationWarning`，测试也不失败。

### 排查结论（两条）

1. `filterwarnings` 的 `module` 部分使用 **`re.match`（前缀匹配）** 去匹配**模块名**
2. `warnings.warn(..., stacklevel=2)` 记录的模块是**调用者**的模块

所以「警告从 `memagent` 内部发出」往往记录成调用者的模块，正则匹配不上。

### 采用方案

**移除该配置。** 改用：
- pytest 默认行为（警告只提示、不失败）
- 需要强制检查时，命令行显式加 `-W error::DeprecationWarning`

> 教训：**配置文件里写了不等于生效。** 任何过滤器、钩子、中间件类配置
> 都必须用一个「故意触发」的用例验证它真的会拦——否则它只是安慰剂。

## EXP-07 日志脱敏的误伤与漏网

日志脱敏规则经历了两轮修正，两次都是**成品演示（而非单元测试）暴露的问题**。

### 问题 A：类型被破坏

第一版 `redact_sensitive` 把所有值转成字符串：

| 输入 | 输出 | 问题 |
|---|---|---|
| `step=1` | `'1'` | int → str |
| `elapsed_ms=18.3` | `'18.3'` | float → str |
| `retry=False` | `'False'` | bool → str |
| `none_val=None` | `'None'` | None → str |
| `count_list=[1,2,3]` | `'[1, 2, 3]'` | list → str |
| `'read'` | `"'read'"` | 多了引号 |

**后果**：日志字段类型不可信，任何基于日志的分析（例如「耗时 > 1s 的工具调用有多少」）
都要先做类型转换，且转换可能失败。

**修正**：改成**保持类型的版本**——只对命中敏感名单的键做替换，其余原样保留并递归处理嵌套 dict。

### 问题 B：`token` 误伤计量字段（更严重）

`SENSITIVE_KEY_MARKERS` 含 `"token"`，而匹配方式是**子串匹配**，于是：

```
prompt_tokens     → [REDACTED]   ❌ 这是计量，不该脱敏
output_tokens     → [REDACTED]   ❌
input_tokens      → [REDACTED]   ❌
total_tokens      → [REDACTED]   ❌
reasoning_tokens  → [REDACTED]   ❌
cached_tokens     → [REDACTED]   ❌
max_output_tokens → [REDACTED]   ❌
```

**后果**：阶段三的验收要求 `generation` 记录 model / token / cost
（AGENTS.md §4.8），这条规则会让 token 消耗**完全不可观测**。

**发现方式**：跑成品演示 `scripts/demo_logging.py` 看实际输出，注意到
`"prompt_tokens": "[REDACTED]"`。

### 修正方案：区分「凭据」与「计量」

| 键 | 判定 | 理由 |
|---|---|---|
| `access_token` / `refresh_token` / `auth_token` | 🔒 脱敏 | 凭据 |
| `token` / `TOKEN` | 🔒 脱敏 | 凭据 |
| `*_tokens`（`prompt_tokens` 等） | 🔓 **保留** | 计量 |
| `api_key` / `password` / `secret` / `dsn` / `credential` | 🔒 脱敏 | 凭据 |

修正后分类表零错误（当前规则有 7 项误脱敏）。

> 已固化为测试：`test_token_metrics_are_not_redacted`、`test_is_sensitive_classification_table`

### 附带发现：降级路径丢了脱敏（安全问题）

`configure_logging()` 的 `except Exception` 降级分支原本没有 `redact_sensitive` processor。
实测后果：**一旦配置读取失败，密钥就会以明文写进日志**：

```
降级后: "api_key": "sk-real-secret-value"     ← 明文落盘
```

**安全保护在降级路径上静默消失**，这是最危险的一类降级。

> 已固化为测试：`test_fallback_path_still_redacts_secrets`

### 核心教训

**这两类错误方向相反**：

| 错误 | 性质 | 后果 |
|---|---|---|
| **漏脱敏** | 安全事件 | 密钥落盘，可能已泄漏 |
| **误脱敏** | 可观测性损失 | token 消耗看不见，阶段三验收卡住 |

两者都要避免，不能因为「脱敏宁严勿松」就容忍误脱敏——
`prompt_tokens` 被脱敏不会有人报警，但会让阶段三的目标无法达成。

## EXP-08 bashkit VFS 一致性与阻塞行为

阶段一「核心设计原则 1」要求 `read` / `write` / `bash` 操作**同一个** VFS。
以下实验用于确认 bashkit 能做到、以及有哪些限制。

### VFS 共享关系

| 关系 | 结论 |
|---|---|
| 同一个 `BashTool` 的 `.fs()` 与 `.execute()` | ✅ **共享同一 VFS**（双向：fs 写的 bash 能读，反之亦然） |
| 独立的 `FileSystem()` 与 `BashTool` | ❌ **完全隔离**（bash 读独立 fs 写的文件报 `file not found`） |

**设计结论**：三者必须由**同一个类**统一持有同一个 `BashTool` 实例，
任何模块都不得自行 `new` 一个。这就是 `SandboxSession` 单例的存在理由。

### 已确认的行为细节

| 行为 | 实测结果 |
|---|---|
| `fs.write_file` 是否自动建父目录 | ❌ **不建**，报 `RuntimeError: io error: parent directory not found` |
| `BashTool.execute()` 的并发安全性 | ✅ 在 `asyncio.gather` 下安全 |
| `fs()` 同步调用是否阻塞事件循环 | ⚠️ **会阻塞**（2MB 写入把 ticker 从 30 压到 21） |
| `timeout_seconds` 触发后 | exit code 1，`error` 字段被设置 |
| `readonly_filesystem` | ✅ 优雅拒绝写入 |
| `cat /missing` | `error=None, exit_code=1, stderr='file not found'` |

### `ExecResult` 字段清单

```
error, exit_code, final_env, stderr, stderr_bytes, stderr_truncated,
stdout, stdout_bytes, stdout_truncated, success, to_dict
```

**关键区分**：`error` **只在资源/基础设施错误时**被设置。

| 场景 | `error` | `exit_code` |
|---|---|---|
| `cat /does-not-exist` | `None` | 1 |
| 超过 `max_commands` | `'resource limit exceeded: maximum command count exceeded (2)'` | — |

**设计结论**：`bash` 工具**不抛异常、不判成败**，把 `(exit_code, stdout, stderr)`
三样原始信息交回上层。理由：AGENTS.md 要求「工具调用超时 → 返回错误信息给模型，
由模型决定换工具或放弃」——若在沙箱层抛异常，模型就拿不到失败详情了。

### `BashkitTool` 包装类的行为（若使用）

| 场景 | 行为 |
|---|---|
| 命令失败（exit 1） | 返回 `'\nSTDERR: ...\n[Exit code: 1]'` |
| 资源超限 | **抛 `ToolException`** |

**设计结论**：不依赖 `BashkitTool`。它内部持有 `_bash_tool` 作为 `PrivateAttr`，
我们无法可靠地拿到同一个 VFS 实例。**决定自己持有原生 `BashTool` 单例。**

### 版本号陷阱

```
bashkit.__version__        → '0.1.2'
实际安装的 wheel 版本       → 0.18.1
```

**不要用 `bashkit.__version__` 做版本判断逻辑。**

## EXP-10 工具设计陷阱：参数存在但不生效

### 现象

`configure_logging()` 曾有一个 `force: bool = False` 参数，作用是「允许重复配置」。

### 真相

- `structlog.configure()` **并没有 `force` 形参**
- 我们的函数也从未使用这个参数
- 所以它**传了等于没传**

### 为什么这是缺陷而非无害

**一个接受参数但忽略它的接口是在说谎。** 调用者传了 `force=True`，
以为「重复配置会生效」，实际什么都没发生——这会让人误判行为、写出依赖不存在语义的代码。

### 检测手段

```python
def test_configure_logging_has_no_dead_parameters() -> None:
    """锁住「参数存在但无效」这个缺陷类别。"""
    params = list(inspect.signature(configure_logging).parameters)
    assert "force" not in params, "force 是死参数：传了不会生效，属于会说谎的接口"
```

### 同类问题清单

| 问题 | 表现 | 检测方式 |
|---|---|---|
| `force` 死参数 | 传了不生效 | 检查函数签名 |
| `filterwarnings` module 参数 | 配置了不生效 | **故意触发**一个警告验证 |
| `TRUNCATED_REPR` 忽略 `limit` | 参数被忽略 | 用不同 limit 值对比输出 |
| 环境变量名写错 | 静默用默认值 | 断言「生效的变量名」列表 |
| 降级路径丢脱敏 | 安全保护消失 | 用 mock 制造配置读取失败 |

### 核心教训

**「参数存在」「配置写了」「代码调用了」都不等于「行为发生了」。**
这类缺陷的共同特点是**不报错**，因此只能靠**故意触发反例**的测试来发现。
本项目对这类问题的统一对策是：**为每一个「应该发生的行为」写一个会失败的验证**。

## 附录：本项目的纪律清单

从上述实验中提炼出的、必须持续遵守的开发纪律：

### 验证纪律

1. **「我这儿能跑」不是证据**——必须给出真实命令输出
2. **验证隔离/拦截/过滤类机制时，必须用「故意触发的反例」**，
   否则无法区分「生效了」与「只是恰好没触发」
3. **Mock 判别值陷阱**：当「被检查的值」与「期望值」相同时，验证无效。
   必须构造差异值——本项目已因此踩坑 3 次
4. **测试必须单独跑也能通过**。结果依赖执行集合就是设计缺陷

### 配置纪律

5. 所有配置经由 `config.py` 流入，**禁止在其他模块直接读 `os.environ`**
6. 变量名必须与「分组前缀 + 字段名」严格对应；
   `extra='ignore'` 会吞掉写错的变量名，**不报错**
7. `.env` 的行内注释一律单独占一行

### 安全纪律

8. 密钥轮换：任何出现在会话记录、日志、终端输出中的 key 都视为已泄漏
9. 降级路径必须保留安全保护（脱敏、鉴权、限流）
10. 断言「敏感值不出现在原始输出中」，而不只是断言字段被替换

### 注释纪律

11. 每个公开符号说明**做什么 + 为什么这么设计 + 怎么用**
12. 踩过的坑就近标注在代码里（一句话 + 原因）
13. 「为什么不用 X 方案」的完整推导写进本文件，不写进代码
14. 本文件每条结论必须附实测输出或官方出处；未验证的明确标注
